# دورة حياة طلب التزويد — من الموافقة إلى دخول البضاعة لمستودع البائع

**الإصدار:** 1.0
**التاريخ:** 2026-08-10
**الحالة:** منفَّذ ومغطّى بـ 12 اختباراً (`tests/Feature/ReplenishmentLifecycleTest.php`)
**المصدر الوحيد للقواعد:** `App\Services\Inventory\ReplenishmentWorkflowService`

---

## 1. المبدأ

طلب التزويد مستند نقل بين موقعين للشركة نفسها: لا بيع، ولا عميل، ولا إيراد.
والشيء الوحيد الذي يجعله حقيقياً هو أن **تنتهي البضاعة في مستودع من طلبها**.

الطريق إلى هناك طريقان، ولهما نتيجتان ماديتان مختلفتان:

| الطريقة | عند الموافقة | عند الاستلام |
|---|---|---|
| **شحن إلى الفرع** (`delivery`) | البضاعة **تغادر** المصدر الآن وتصبح «على الطريق» | تدخل مستودع الفرع |
| **استلام من المستودع** (`pickup`) | البضاعة **تبقى على الرف** محجوزة | تخرج من المصدر وتدخل الفرع **في اللحظة نفسها** |

> **لماذا الفصل ضروري:** لو عوملت طريقة الاستلام كشحن، لخرجت البضاعة من رصيد
> المستودع الرئيسي وهي ما تزال على رفّه — فكل من يسأل «ماذا نستطيع أن نبيع
> اليوم؟» يُجاب بأقل من الحقيقة طوال المدة التي يستغرقها المندوب في الوصول.

## 2. المراحل

```
                         ┌──────────────────────────────┐
   البائع يرسل الطلب ──► │ pending — بانتظار الموافقة   │
   (تُحجز الكميات        └──────────────┬───────────────┘
    في المصدر)                          │
                         موافقة المستودع المصدر
                    ┌────────────────────┴────────────────────┐
                    │                                          │
        fulfillment_method = delivery            fulfillment_method = pickup
                    │                                          │
                    ▼                                          ▼
    ┌───────────────────────────────┐         ┌────────────────────────────────┐
    │ in_transit — قيد النقل        │         │ ready_for_pickup — جاهز للاستلام│
    │ خرجت من المصدر فعلاً          │         │ ما تزال على رفّ المصدر محجوزة   │
    └───────────────┬───────────────┘         └────────────────┬───────────────┘
                    │                                          │
              الفرع يستلم                          المندوب يستلم بنفسه
              (رِجل الدخول)                    (رِجل الخروج + الدخول معاً)
                    └────────────────────┬─────────────────────┘
                                         ▼
                              ┌─────────────────────┐
                              │ completed — البضاعة │
                              │ في مستودع الطالب     │
                              └─────────────────────┘

   الإلغاء متاح من الطرفين ما دامت البضاعة على رفّ المصدر
   (pending أو ready_for_pickup) ⇒ يُحرَّر الحجز.
```

## 3. القواعد

| # | القاعدة |
|---|---------|
| **T1** | الطلب يحجز الكميات في المصدر فوراً ولا يحرّكها. |
| **T2** | **الموافقة تخصّ المصدر** — المستودع المطلوب منه هو من يقرّر، لأنه من يعرف إن كان يستطيع تجهيز سائق اليوم. |
| **T3** | **الاستلام يخصّ الوجهة** — لا يوقّع أحد بالنيابة عن الفرع. |
| **T4** | `delivery`: الخروج عند الموافقة، والدخول عند الاستلام (رِجلان مفصولتان زمنياً). |
| **T5** | `pickup`: لا حركة عند الموافقة، والرِجلان معاً عند الاستلام. |
| **T6** | الكميات المستلمة تُؤخذ **لكل سطر**؛ الشحنة الناقصة والاستلام الجزئي حالتان عاديتان. |
| **T7** | ما لم يأخذه المندوب في الاستلام الجزئي **يُحرَّر حجزه فوراً** ويعود للبيع. |
| **T8** | الشحنة التي تصل ناقصة تُسجَّل فروقاتها (`discrepancies`) ولا تُبتلع بصمت. |
| **T9** | الإلغاء ممكن ما دامت البضاعة لم تغادر؛ بعد المغادرة هو **إرجاع** بحركاته الخاصة لا إلغاء. |
| **T10** | كل رِجل لها مفتاح حركة فريد (`transfer:{id}:item:{itemId}:out|in`) — فإعادة تنفيذ الخطوة لا تحرّك البضاعة مرتين. |

## 4. ما كان معطوباً

| # | العطل | الأثر |
|---|---|---|
| 1 | **لا وجود لمفهوم الاستلام من المستودع** | المندوب الذي يمرّ ويأخذ البضاعة بنفسه لا يجد مساراً يعبّر عن ذلك |
| 2 | **لا خطوة موافقة في التطبيق** | طلب الفرع يبقى `pending` حتى يفتح أحدهم لوحة الإدارة |
| 3 | **`index` يفلتر على `to_warehouse_id` فقط** | موظف المستودع الرئيسي **لا يرى ولا طلباً واحداً** مرفوعاً إليه — فلا شيء يمكن الموافقة عليه من التطبيق أصلاً |
| 4 | **قواعد الدورة مكتوبة مرتين** | `InventoryTransferController` و`FieldReplenishmentController` نسختان تباعدتا فعلاً: استلامٌ بلا كميات صريحة كان يعني «لا شيء» في الأولى و«كل ما شُحن» في الثانية |
| 5 | **`receive` في لوحة الإدارة يشترط `items`** | نداء بلا أسطر كان **يُغلق التحويل مكتملاً دون إدخال أي كمية** — بضاعة خرجت من المصدر ولم تُقيَّد في أي مكان |
| 6 | **`transfer_number` من `count() + 1`** | العمود فريد، فحذف أي تحويل يجعل الإدراج التالي يفشل |

الإصلاح لـ (4): كل شيء يمرّ الآن عبر `ReplenishmentWorkflowService`، والوحدتان
تستدعيانه. أي قاعدة تُضاف تصل الطرفين معاً.

## 5. عقد الـ API

### 5.1 `GET /api/v1/field/replenishment`

| معامل | القيم | الوصف |
|---|---|---|
| `direction` | `all` (افتراضي) · `incoming` · `outgoing` | `incoming` ما طلبتَه، `outgoing` ما طُلب منك |
| `awaiting_my_action` | `1` | ما ينتظر تصرّفاً منك أنت تحديداً |
| `open_only` | `1` | استبعاد المكتمل والملغي |
| `status` | إحدى الحالات | |

كل سجل يحمل ما يستطيع القارئ فعله، محسوباً على الخادم:

```jsonc
{
  "status": "ready_for_pickup",
  "status_text": "جاهز للاستلام من المستودع",
  "fulfillment_method": "pickup",
  "fulfillment_method_text": "استلام من المستودع",
  "direction": "incoming",        // incoming | outgoing | both
  "can_approve": false,           // موافقة = تخصّ المصدر
  "can_receive": true,            // استلام  = تخصّ الوجهة
  "can_cancel": true,
  "is_awaiting_pickup": true
}
```

> **التطبيق لا يشتقّ أياً من هذه الأزرار.** الخادم يحسبها بنفس قواعد الـ workflow،
> فلا يعرض التطبيق زراً سترفضه الواجهة البرمجية.

### 5.2 `POST /api/v1/field/replenishment`

يقبل `preferred_fulfillment_method` (`delivery` | `pickup`) — **تفضيل لا قرار**.

### 5.3 `POST /api/v1/field/replenishment/{id}/approve`

```json
{ "fulfillment_method": "delivery" }
```

| النتيجة | |
|---|---|
| `delivery` | الحالة ⇒ `in_transit`، وتُكتب حركات خروج من المصدر |
| `pickup` | الحالة ⇒ `ready_for_pickup`، ولا تُكتب أي حركة |
| ليس من المصدر | **403** |
| الطلب ليس `pending` | **422** |

### 5.4 `POST /api/v1/field/replenishment/{id}/receive`

```json
{ "items": [ { "product_id": 111, "quantity_received": 5 } ] }
```

`items` اختياري — غيابه يعني «كل ما أُرسل». الاستجابة تحمل:

```jsonc
"effects": {
  "movements": [ 91, 92 ],
  "discrepancies": [
    { "product_id": 111, "product_name": "…", "shipped": 6, "received": 5, "missing": 1 }
  ]
}
```

| الحالة | |
|---|---|
| ليس من الوجهة | **403** |
| كمية أكبر مما أُرسل | **422** |

### 5.5 `POST /api/v1/field/replenishment/{id}/cancel`

`{ "reason": "…" }` — متاح للطرفين ما دامت البضاعة لم تغادر، وإلا **422**.

### 5.6 لوحة الإدارة

`POST /admin/inventory-transfers/{id}/ship` يقبل الآن `fulfillment_method`
(الافتراضي `delivery`، وهو ما كان يفعله دائماً)، و`receive` صار `items` فيه
اختيارياً — انظر العطل رقم 5.

## 6. تدفّق التطبيق

```
موظف الفرع                                   موظف المستودع الرئيسي
─────────                                    ──────────────────────
شاشة التزويد ──► يحدّد الأصناف
                 يختار الطريقة المفضّلة
                 يرسل ──────────────────────► «طلبات عليّ» (direction=outgoing)
                                                      │
                                              [موافقة] ──► نافذة الطريقة:
                                                            • شحن إلى الفرع
                                                            • استلام من المستودع
                                                      │
«طلباتي» ◄────────────────────────────────────────────┘
     │
[تأكيد الاستلام] ──► نافذة الكميات (قابلة للتخفيض إن وصل أقل)
     │
     ▼
البضاعة في مستودع الفرع
```

## 8. الترحيل

`2026_08_10_120000_add_fulfillment_method_to_inventory_transfers`

- `fulfillment_method` · `approved_at` · `approved_by` (كلها nullable)
- `status`: من `enum` إلى `varchar` — لأن كل مرحلة جديدة كانت ستصبح ترحيلاً
  للمخطط على جدول تكتب فيه واجهتان، ومع SQLite (قاعدة الاختبارات) إعادةَ بناءٍ
  للجدول كاملاً في كل مرة. القيم ثوابت على النموذج، وهو مكانها في هذا المشروع.

**نُفِّذ على قاعدة البيانات الحيّة وتم التحقق:** الأعمدة موجودة، ونوع `status`
صار `varchar(255)`، ولا تحويلات قائمة تأثّرت.
