## 1. المشكلة التي يحلّها هذا الفلتر

البائع الميداني يبيع من على رفّ الفرع الذي يقف فيه. قبل هذا التنفيذ كان أمام
الكمية غير الكافية مساران، وكلاهما سيّئ:

| السلوك السابق | النتيجة |
|---|---|
| التطبيق يمنع تجاوز رصيد الفرع (`exceedsAvailableStock`) | البيع يسقط أمام العميل رغم توفّر البضاعة في المستودع الرئيسي |
| الطلب يُنشأ ثم يفشل عند التأكيد | العميل سمع "تمّ"، والنظام يقول "لا" — والحجز لم يحدث |

**الفلتر يقلب الترتيب:** يُحسب أولاً ما يغطيه مستودع البائع، ثم يُعرض النقص على
المستودع الرئيسي، ويُسأل البائع سؤالاً واحداً صريحاً قبل أن يُكتب أي شيء.

## 2. القواعد

| # | القاعدة |
|---|---------|
| **F1** | الطلبية تُخدَم افتراضياً من **مستودع البائع وحده** (`employees.warehouse_id`). |
| **F2** | ما لا يغطيه الفرع يُعرض على **المستودع الرئيسي** (`warehouses.is_primary = 1` و `is_active = 1`). |
| **F3** | السحب من المستودع الرئيسي **لا يتم تلقائياً** — يتطلب موافقة صريحة عبر `supply_from_main`. |
| **F4** | الكمية المكمِّلة تُكتب في **بند مستقل** يحمل اسم المستودع الرئيسي في `description`. |
| **F5** | ما يعجز عنه المستودعان معاً **يُرفض الطلب كاملاً** — ولا تُقلَّص الكمية تلقائياً. |
| **F6** | التوزيع يُحسب **على الخادم** في كل مرة، ولا يُقرأ من حمولة التطبيق أبداً. |
| **F7** | كل بند — حتى بند الفرع العادي — يحمل `sales_order_item_allocations` يحدّد مصدره. |
| **F8** | المعاينة (`preview`) **لا تحجز ولا تكتب** أي شيء. |

### 2.1 تعريف "المتاح" — نقطة حرجة

```
المتاح = available_quantity - reserved_quantity
```

وهو **بالضبط** ما تختبره `InventoryService::reserve()` قبل أن تحجز. يوجد في
المشروع تعبير آخر (`quantity - reserved - damaged - quarantined`) تستخدمه شاشات
عرض المخزون، وهو يساوي الأول عددياً ما دام `quantity = available + damaged +
quarantined` (وهي معادلة تحافظ عليها `InventoryService`).

> **السبب في التمسّك بالصيغة الأولى:** الوعد الذي يُقطع للعميل يجب أن يُختبر
> بنفس الأداة التي ستُطالَب بتنفيذه لاحقاً. لو بُنيت الخطة على تعريف مختلف،
> لعُرضت على البائع كميات يرفض الحجز إعطاءها، فيتحوّل بيع مؤكَّد إلى رسالة خطأ.

## 3. نطاق الصلاحية — ما يراه البائع وما يتصرّف فيه

الفلتر يفصل بين سؤالين كانا يُخلطان في قائمة واحدة:

| السؤال | المصدر في `FieldScope` | يشمل |
|---|---|---|
| **من أين يحقّ لي أن أبيع/أتصرّف؟** | `warehouseIds()` | مستودع البائع فقط (إن كان مقيَّداً) |
| **من أين يجوز للشركة أن تموّلني؟** | `supplyWarehouseId()` | المستودع الرئيسي |
| **ما الأرصدة التي يحقّ لي قراءتها؟** | `visibleWarehouseIds()` | الاثنان معاً — **للقراءة فقط** |

`supplyWarehouse()` تُعيد `null` إذا كان البائع يعمل أصلاً في المستودع الرئيسي
(تكملة من نفسك ليست تكملة)، أو إذا لم يُعرَّف مستودع رئيسي نشط.

> **لماذا الفصل ضروري:** نقاط النهاية التي تُحرّك البضاعة (إنشاء طلب، استلام
> تزويد، سجل الحركات) تسأل `warehouseIds()` وحدها ولم تتغيّر. توسيع تلك القائمة
> بالمستودع الرئيسي كان سيمنح كل حساب فرع تصرّفاً في مخزون الشركة كله — بينما
> المطلوب هو **رؤية** الرصيد لا **التصرّف** فيه.

## 4. الخوارزمية

`App\Services\Field\BranchOrderSourcingService::plan()`

```
لكل منتج في الطلب (بعد دمج البنود المكرّرة لنفس المنتج):

    branch_available  = المتاح في مستودع البائع
    from_branch       = min(requested, branch_available)
    shortage          = requested - from_branch

    supply_available  = المتاح في المستودع الرئيسي
    from_supply       = min(shortage, supply_available)
    unavailable       = shortage - from_supply
```

**دمج البنود المكرّرة** مقصود: لو أُرسل نفس المنتج في سطرين بكمية 5 لكلٍّ منهما
ورصيد الفرع 5، فقياس كل سطر على حدة يُنجح الاثنين ويَعِد بـ 10 وحدات من رفّ
يحمل 5.

### 4.1 مخرجات الخطة

| الحقل | المعنى |
|---|---|
| `is_fully_covered_by_branch` | الفرع يغطي كل شيء — لا سؤال ولا بند إضافي |
| `needs_supply` | هناك كمية ستُسحب من المستودع الرئيسي — **هذا هو محفّز السؤال** |
| `can_fulfil` | `false` عندما يعجز المستودعان معاً — لا فائدة من أي إجابة |
| `supply_summary` | نص السؤال جاهزاً للعرض |
| `blocked_summary` | نص الرفض مع أقصى ما يمكن تأمينه لكل بند |

> **الرسائل تُصاغ على الخادم لا في التطبيق**، حتى لا يصف الهاتف والمكتب الخلفي
> نفس النقص بعبارتين مختلفتين.

## 5. بناء البنود

`BranchOrderSourcingService::buildLines()`

بند واحد ناقص يتحوّل إلى **بندين**:

| البند | الكمية | `description` | التخصيص |
|---|---|---|---|
| بند الفرع | `from_branch` | `null` | مستودع البائع |
| **البند المكمِّل** | `from_supply` | `كمية مكمِّلة من {اسم المستودع الرئيسي}` | المستودع الرئيسي |

**لماذا بندان لا بند واحد مع ملاحظة؟** النصفان يُجهَّزان في مبنيين مختلفين على
يد شخصين مختلفين. بند واحد يقول عكس ذلك. والانقسام ليس وصفياً فقط: كل بند يحمل
`sales_order_item_allocations`، وهو ما تحجز عليه `SalesOrderWorkflowService` عند
التأكيد وتشحن منه لاحقاً — فتتطابق الأوراق مع البضاعة.

**الخصم** يبقى كاملاً على بند الفرع ولا يُوزَّع على الانقسام، وإلا اختلف إجمالي
الطلبية نفسها باختلاف ما صادف وجوده على الرف.

**السعر** واحد في البندين — البضاعة نفسها، ويُقرأ من الكتالوج لا من الطلب.

## 6. عقد الـ API

### 6.1 `POST /api/v1/field/orders/preview`

معاينة لا تكتب ولا تحجز. تُستدعى أثناء إدخال الكمية.

```jsonc
// الطلب
{ "items": [ { "product_id": 111, "quantity": 10 } ] }
```

```jsonc
// الاستجابة 200
{
  "success": true,
  "message": "الكمية المتاحة في مستودعك لا تكفي: … هل ترغب بطلب الكمية الناقصة من \"المستودع الرئيسي\"؟ …",
  "data": {
    "sourcing": {
      "branch_warehouse": { "id": 2, "name": "فرع جدة", "code": "WH-JED" },
      "supply_warehouse": { "id": 1, "name": "المستودع الرئيسي", "code": "WH-MAIN" },
      "lines": [{
        "product_id": 111,
        "product_name": "خلاط مغسلة",
        "requested": 10,
        "branch_available": 3,
        "from_branch": 3,
        "shortage": 7,
        "supply_available": 50,
        "from_supply": 7,
        "unavailable": 0,
        "needs_supply": true,
        "is_covered": true
      }],
      "is_fully_covered_by_branch": false,
      "needs_supply": true,
      "can_fulfil": true,
      "supply_summary": "…",
      "blocked_summary": null
    }
  }
}
```

> المعاينة لا تحجز عمداً: معاينتان لآخر وحدة ستقولان كلتاهما إنها موجودة،
> وواحدة فقط ستحصل عليها عند التأكيد. البديل — معاينة تحجز — يجعل مسوّدة
> مهجورة تجلس على مخزون لا يستطيع أحد بيعه.

### 6.2 `POST /api/v1/field/orders`

يُضاف حقل واحد إلى الحمولة القائمة:

```jsonc
{ "supply_from_main": true }   // إجابة البائع على السؤال. غيابه = لا.
```

| الحالة | الرمز | `data.reason` |
|---|---|---|
| الفرع يغطي الطلب | `201` | — |
| نقص + `supply_from_main: true` | `201` | — (مع `has_supply_lines: true`) |
| نقص بلا موافقة | `422` | `supply_confirmation_required` |
| يعجز عنه المستودعان | `422` | `insufficient_stock` |

الحالتان `422` تحملان `data.sourcing` كاملاً — وهو ما يبني منه التطبيق نافذته.

```jsonc
// استجابة 201 بعد الموافقة
{
  "success": true,
  "message": "تم إنشاء الطلب وتأكيده وحجز المخزون. وأُضيف 1 بند مكمِّل من المستودع الرئيسي.",
  "data": {
    "order": { "…": "…" },
    "has_supply_lines": true,
    "lines": [
      { "quantity": 3, "is_supply_line": false, "sources": [{ "warehouse_name": "فرع جدة", "quantity": 3 }] },
      { "quantity": 7, "is_supply_line": true,
        "description": "كمية مكمِّلة من المستودع الرئيسي",
        "sources": [{ "warehouse_name": "المستودع الرئيسي", "quantity": 7 }] }
    ]
  }
}
```

> **`supply_from_main` إذنٌ لا تعليمةُ توزيع.** التطبيق يقول "يجوز السحب"،
> والخادم يقرّر "كم ومن أين" مقابل الرصيد اللحظي — فخطة حسبها الهاتف قبل دقيقة
> لا تستطيع أن تلتزم بوحدات بيعت منذ ذلك الحين.

### 6.3 `GET /api/v1/field/inventory/products/{product}`

أُضيف حقلان:

| الحقل | المعنى |
|---|---|
| `supply_available` | رصيد المستودع الرئيسي — معروض منفصلاً |
| `warehouses[].is_supply_source` | يميّز صفّ المستودع الرئيسي |

`total_available` **يستثني** المستودع الرئيسي عمداً: دمجه في الرقم يقرأ كأنه
"لديك هذا القدر"، وهو الالتباس نفسه الذي وُجد الفصل لتجنّبه.

## 7. الأثر على دورة حياة الطلبية

الطلبية المكمَّلة تمرّ في نفس المسار (`pending → confirmed → …`)، لكن التأكيد
لم يكن ليمرّ قبل تعديلين في `SalesOrderWorkflowService`:

| الدالة | قبل | بعد |
|---|---|---|
| `assertCanCover()` | تقيس كل بند مقابل **مستودع تنفيذ الطلب وحده** | تقيس كل بند مقابل **مصادره المخطَّطة** عبر `shipmentSourcesFor()` |
| `sellableFor()` | تُعيد حجز الطلب لنفسه فقط عند مستودع التنفيذ | تُعيده عبر `ownHoldAt()` من خطة المصادر — لكل مستودع على حدة |

بدون الأول، أي طلب يحمل بنداً مكمِّلاً كان **يستحيل تأكيده**: البند يُقاس مقابل
رفّ الفرع الذي لا يملكه أصلاً. الدالة الآن تطابق `reserveAll()` التي كانت
تراعي المصادر أصلاً — فصار السؤال المطروح في الفحص هو نفسه السؤال في التنفيذ.

**النتيجة عند التأكيد** (مثبتة باختبار): 3 وحدات محجوزة في الفرع، و7 في
المستودع الرئيسي — كلٌّ حيث ستُسحب فعلاً.

### 7.1 ما لا يفعله هذا الفلتر

البند المكمِّل **يَحجز ثم يُخرج** الوحدات من المستودع الرئيسي عند الشحن. أما
**النقل الفعلي** للبضاعة إلى الفرع (أو تسليمها للعميل من المستودع الرئيسي)
فعملية تشغيلية منفصلة تُدار عبر `/field/replenishment`
(`inventory_transfers`). الفلتر يضمن صحّة الأرقام والحجز والقيود — لا يحرّك
شاحنة.

## 8. تدفّق التطبيق (Flutter)

```
البائع يزيد الكمية فوق رصيد الفرع
        │
        ├─► previewLocalOrder()  ──► تلميح أسفل حقل الكمية بالتوزيع المتوقَّع
        │
        └─► إرسال الطلبية
                │
                ├─ 201 ──────────────► نجاح (+ إشعار بالبند المكمِّل إن وُجد)
                │
                ├─ 422 supply_confirmation_required
                │        └─► showSupplyConfirmationDialog()
                │                ├─ موافقة ──► إعادة الإرسال بـ supply_from_main: true
                │                └─ رفض ────► العودة لتعديل الكمية
                │
                └─ 422 insufficient_stock ──► showUnsourceableDialog()
```

**الملفات:**

| الملف | الدور |
|---|---|
| `lib/models/order_sourcing_model.dart` | `OrderSourcingPlan` / `OrderSourcingLine` |
| `lib/widgets/staff/supply_confirmation_dialog.dart` | نافذة السؤال + نافذة التعذّر |
| `lib/data/field_requests_repository.dart` | `previewLocalOrder` / `createLocalOrder` |
| `lib/providers/field_requests_provider.dart` | `pendingSourcing` — تفصيل الرفض |
| `lib/screens/staff/staff_local_order_screen.dart` | التدفّق أعلاه |
| `lib/core/api/api_exception.dart` | `data` — حمولة الـ 422 |

**تغيير سلوكي مقصود:** حُذف تحقّق `exceedsAvailableStock` من حقل الكمية، وأُزيل
سقف زر `+`. تجاوز رفّ الفرع لم يعد خطأ إدخال — بل هو الحالة التي وُجدت التكملة
من أجلها. والهاتف على أي حال يعرف ما كان على الرف لحظة فتح الشاشة لا ما عليه
الآن، ولا يعرف شيئاً عن المستودع الرئيسي.

## 10. إصلاحان جانبيان لزما لتشغيل ما سبق

1. **`2026_08_09_000001_create_sales_order_item_allocations_table.php`** — كان
   يفحص وجود الفهرس عبر `information_schema.statistics` (MySQL حصراً). على
   SQLite — وهي قاعدة بيانات الاختبارات — الاستعلام ليس فارغاً بل **قاتل**، فكان
   يمنع كل هجرة بعده ويُعطّل تشغيل أي اختبار في المشروع. استُبدل بـ
   `Schema::getIndexes()`.

2. **`tests/Feature/DashboardApiTest.php`** — يشير إلى `Invoice::STATUS_PAID`
   وهو ثابت غير موجود (السداد يُتابَع عبر `paid_amount`/`due_amount`، و`status`
   يسجّل المرحلة). صُحّح إلى `STATUS_DELIVERED`. لم يكن الخلل ظاهراً لأن الهجرة
   أعلاه كانت تُسقط الاختبارات قبل أن تصل إليه.

## 11. التزويد الاستباقي — قبل أن ينفد الصنف

القسم السابق يعالج النقص **لحظة البيع**. لكن الأفضل ألّا يصل الفرع إلى تلك
اللحظة أصلاً، وهو ما تخدمه شاشة التزويد.

### 11.1 ما كان معطوباً

| المشكلة | الأثر |
|---|---|
| لا قائمة بما ينقص | التزويد يعتمد على ذاكرة الموظف؛ صنف لم ينتبه له أحد ينفد |
| لا رؤية للمستودع الرئيسي | الطلب تخمين يُرفض بعد الإرسال |
| صنف واحد لكل طلب | تزويد 8 أصناف = 8 تحويلات منفصلة على المستودع أن يجهّزها ويتابعها |
| لا كمية مقترحة | الموظف يكتب رقماً من رأسه |
| الرفض عند أول صنف ناقص | يكتشف النواقص واحداً تلو الآخر، وكل محاولة تُلغي الباقي |
| زر «طلب من الرئيسي» يظهر عند الصفر فقط | الصنف المنخفض لا يُزوَّد **حتى ينفد فعلاً** |

### 11.2 القواعد

| # | القاعدة |
|---|---------|
| **R1** | يُدرَج الصنف حين `المتاح ≤ حد إعادة الطلب` — ويشمل النافد. |
| **R2** | الترتيب: النافد أولاً، ثم الأكثر نقصاً — ترتيب من يعمل بالقائمة فعلاً. |
| **R3** | `target_level = max(reorder_point, (متوسط البيع اليومي × مدة التوريد) + مخزون الأمان)`. |
| **R4** | `suggested = target_level - available`، وعند الصفر يُقترح حدٌّ كامل. **الاقتراح قابل للتعديل دائماً.** |
| **R5** | كل سطر يحمل رصيد المستودع الرئيسي و`supply_covers` — النقص يُرى **قبل** الإرسال. |
| **R6** | الطلب الواحد يغطي كل الأسطر المحددة (تحويل واحد). |
| **R7** | الرفض يذكر **كل** سطر ناقص، وهو ذرّي: لا كتابة ولا حجز جزئي. |

### 11.3 تجربة الموظف

```
لوحة التحكم ──► عدّاد «منخفض» أو «نافد» (قابل للنقر)
شاشة المخزون ──► تفاصيل صنف ──► «طلب من المستودع الرئيسي»
                                        │
                                        ▼
                              شاشة التزويد
   ┌────────────────────────────────────────────────────┐
   │ ملخّص: نافد 2 · منخفض 6 · 45 وحدة مقترحة            │
   │ ⚠ صنف واحد لا يغطيه المستودع الرئيسي بالكامل        │
   ├────────────────────────────────────────────────────┤
   │ [الكل 8] [نافد 2] [منخفض 6] [غير متوفر بالكامل 1]   │
   ├────────────────────────────────────────────────────┤
   │ ☑ [نافد] خلاط مغسلة              SKU-MIXER          │
   │   ▓░░░░░░░░░  لديك 0 من 10                          │
   │   🏬 متاح في الرئيسي: 50                             │
   │   ─────────────────────────────                     │
   │   الكمية المطلوبة      ⊖   10   ⊕                   │
   ├────────────────────────────────────────────────────┤
   │ [ملاحظات...]                                        │
   │ ✕   [ 🚚 طلب 3 صنف (24 وحدة) ]                      │
   └────────────────────────────────────────────────────┘
```

**قرارات واجهة مقصودة:**

| القرار | السبب |
|---|---|
| عدّاد الكمية **مسقوف** برصيد المستودع الرئيسي | سطر واحد متجاوز يُسقط الطلب كله ومعه بقية الأسطر |
| صنف برصيد صفر في الرئيسي **غير قابل للتحديد** | لا يمكن أن يكون جزءاً من طلب اليوم |
| الشريط السفلي يظهر **بعد** أول تحديد | القائمة تبقى مكشوفة والموظف ما زال يقرّر |
| البحث عند **الإرسال** لا مع كل حرف | الاستعلام يعمل على الخادم؛ حرفٌ = طلبٌ على شبكة الهاتف |
| الصف المرفوض **مُحاط بإطار أحمر** + زر «اضبط الكميات تلقائياً» | الموظف يرى أي الأسطر أخفق ويصلحها دفعةً واحدة |
| «إنشاء طلبية» و«طلب تزويد» يظهران **معاً** | الصنف المنخفض يُباع **ويُزوَّد** — وهما ليسا بديلين |

## 12. حدود معروفة

| الحد | الاعتبار |
|---|---|
| مصدر تكملة واحد فقط (المستودع الرئيسي) | التوزيع متعدّد المستودعات متاح أصلاً عبر `OrderAllocationService` لمسار السلة. هذا الفلتر يخدم القرار الميداني البسيط: رفّي، ثم المخزن الرئيسي. |
| المعاينة لا تحجز | مقصود — انظر §6.1. الحجز الحقيقي عند التأكيد، وقد يرفض إن تغيّر الرصيد. |
| الرفض عند العجز الكلي | قرار عمل: تقليص الكمية تلقائياً يبيع العميل أقلّ مما طلب دون أن يُخبره أحد. |
| البند المكمِّل لا يُنشئ أمر نقل تلقائياً | النقل عملية تشغيلية منفصلة — انظر §7.1، وشاشة التزويد في §11 هي الأداة. |
| الكمية المقترحة تعتمد على `reorder_point` | صنف بلا حد مُعرَّف يُقترح له الحد الأدنى فقط. ضبط حدود إعادة الطلب يحسّن الاقتراح مباشرة. |
| اقتراحات التزويد لا تحجز | مثل المعاينة: رصيد المستودع الرئيسي قد يتغيّر قبل الإرسال، والرفض عندها يذكر كل سطر ناقص. |
